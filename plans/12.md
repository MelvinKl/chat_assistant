# Issue #12 — Extend question answering with preprocessing and postprocessing stages

## Summary

Question answering gains two **stages** — *preprocessing* and *postprocessing* — each carrying its own system prompt, its own selection of available MCP servers, and an optional **SystemOne** model that limits the tools available to the LLM at that stage (new `stages.feature`, 5 scenarios). The chat graph grows from four to six processing nodes and runs `START → preprocessing → determine_language ∥ rephrase_question → decide → rephrase_answer → postprocessing → END`. The prompt settings family, the dependency container bindings, MCP `agent` tool routing, and the helm chart's prompt environment variables follow, and the arc42 tree plus README are brought to the post-delta state. The oracle grows from 128 scenarios in 14 feature files, drops the nine `code-weaver-workflow` scenarios (the workflow file is not requirements-tracked — its requirement file and test module are removed from the repository) and adds `stages.feature` (5), `configuration` (1) and `mcp-integration` (2), settling at **127 in 14**.

## Description

**Run shape.** This is a standing in-place delta, **not** the brownfield shape: four of the five changed requirement files exist in the run's baseline and are *changed*, one (`stages.feature`) is *new*. The brownfield clause therefore does not apply — the standing instructions govern, and this plan implements the delta in the system and keeps the test oracle aligned with it.

**The delta per file** — 5 **adjusted** scenarios (existing scenarios whose body, or title and body, changed) and 8 **new** scenarios:

| File | Adjusted | New |
|---|---|---|
| `requirements/chat-graph.feature` | 3 — *the graph contains the six processing nodes* (retitles the four-node scenario; the node table gains `preprocessing` and `postprocessing`); *the graph starts with the preprocessing step* (replaces *the graph starts both language detection and question rephrasing* — `START` now fans out from the new preprocessing node instead of directly); *language detection and decision converge into the answer rephrasing* (title unchanged; `rephrase_answer` now feeds the new postprocessing node, which ends the graph) | — |
| `requirements/configuration.feature` | 1 — *the prompt settings are read from the environment* (the Given widens from "the four `SETTINGS_PROMPTS_` environment variables" to "the `SETTINGS_PROMPTS_` environment variables"; the settings additionally carry the preprocessing and postprocessing system prompts) | 1 — *the container binds the preprocessing and postprocessing stages* |
| `requirements/helm-deployment.feature` | 1 — *the prompt settings are rendered as environment variables* (the rendered prompt environment variables additionally include the preprocessing and postprocessing system prompts) | — |
| `requirements/mcp-integration.feature` | — | 2 — *a server assigned to the preprocessing stage registers its tools for that stage*; *a server assigned to the postprocessing stage registers its tools for that stage* |
| `requirements/stages.feature` (new file) | — | 5 — every scenario of the new feature file |

The other feature files of the oracle are unchanged; their guard areas stay green untouched. Total: 128 → **127 scenarios in 14 files** (the nine `code-weaver-workflow` scenarios are removed from the oracle — the workflow file is not requirements-tracked — while `stages.feature` adds five, `configuration` one and `mcp-integration` two).

**Documentation grounding and gap (hard rule 2).** The arc42 tree (established by the issue-11 run) documents the *pre-delta* system: the four-node graph (5.2 decision "How a chat request is processed", 7.2/7.5 building blocks, the 8.1 scenario 1 runtime diagram, glossary "chat graph"/"graph node"), the four-prompt `PromptSettings` family (the I2 table, the 9.1 `assistant-cm` row, the README Prompts table, and the 11.8 risk row), the MCP `agent` key as null-or-subagent-name (5.2 "What the agent is", the glossary "MCP server"/"tool" entries, the README MCP Server table), and the 14-file/128-scenario tables (03, 10.2, 13). This delta introduces one component and one term that arc42 does not mention **anywhere**: the question answering **stages** and the **SystemOne** model. The plan says so and plans around it: the stages' shape is derived solely from the `stages.feature` description (own system prompt; own selection of available MCP servers — realized by extending the documented `agent` key with the two stage names; optional SystemOne model limiting the stage LLM's tools, else the documented main LLM) plus the documented patterns (the settings pattern, one composition root, LLM creation from settings — 7.4, I2/I3). The feature file fixes the SystemOne *contract* (optional; when configured, the stage LLM's tools are limited; when absent, the stage runs on the main LLM) but not its *configuration mechanism* — the implementation follows the documented settings pattern, and step 7 records the chosen shape in the glossary. The run updates the documentation tree to the post-delta state so the 5.2 "How the system is documented" decision (one structured, machine-navigable source; discrepancies recorded, not hidden) stays honest.

**Oracle mechanics (chapter 10.2).** The coverage guard (`tests/test_scenario_coverage.py`) is parametrised per feature file and checks both directions. Against this delta, until the steps below land: two retired chat-graph titles would dangle (guard 2) and the 8 new scenarios would be uncovered (guard 1). Each area's step lands that area's oracle edits, so the guard turns green per area as the steps land and is fully green at the gate step. No `xfail` pin is planned — this run implements every new and adjusted scenario.

## Acceptance Criteria

- **AC1** — *adjusted — configuration.feature, "the prompt settings are read from the environment"*: the prompt settings family carries the preprocessing and postprocessing system prompts alongside the four existing rephrasing prompts, read from the `SETTINGS_PROMPTS_*` environment variables; the four prior prompt expectations still hold.
- **AC2** — *new — configuration.feature, "the container binds the preprocessing and postprocessing stages"*: configuring the dependency container binds the preprocessing stage with the preprocessing system prompt and the postprocessing stage with the postprocessing system prompt; the unchanged "the container binds the agent components" still holds.
- **AC3** — *new — stages.feature, "the preprocessing stage runs with its own system prompt" / "the postprocessing stage runs with its own system prompt"*: the preprocessing stage's LLM call (on the question) carries the preprocessing system prompt; the postprocessing stage's LLM call (on the returned answer) carries the postprocessing system prompt.
- **AC4** — *new — stages.feature, "a stage receives the tools of its available MCP servers" / "a SystemOne model limits the tools available to the stage LLM" / "the SystemOne model is optional"*: a stage LLM receives the tools of the stage's available MCP servers; a stage with a configured SystemOne model runs its LLM on that model with the tools available to it limited; a stage without one runs on the main LLM.
- **AC5** — *new — mcp-integration.feature, "a server assigned to the preprocessing stage registers its tools for that stage" / "a server assigned to the postprocessing stage registers its tools for that stage"*: an MCP server whose `agent` field is `preprocessing` / `postprocessing` registers its tools under the respective stage; the unchanged "server tools are grouped by their agent assignment" (main agent, named subagent) still holds.
- **AC6** — *adjusted — chat-graph.feature, "the graph contains the six processing nodes" / "the graph starts with the preprocessing step" / "language detection and decision converge into the answer rephrasing"*: the graph contains the six processing nodes including `preprocessing` and `postprocessing`; `START` connects to `preprocessing`, which connects to both `determine_language` and `rephrase_question`; `rephrase_answer` connects to `postprocessing`, which connects to `END`; all nine unchanged chat-graph scenarios — including "the invocation result is the processed answer" and "an empty request yields the no question answer" — still hold.
- **AC7** — *adjusted — helm-deployment.feature, "the prompt settings are rendered as environment variables"*: the rendered assistant settings config map carries the preprocessing and postprocessing system prompts as environment variables alongside the four documented ones; the unchanged "the rendered assistant environment matches the settings the application reads" and "the default values contain only keys consumed by the chart templates" still hold — the new values keys are consumed by the settings config map template, and the rendered keys match the prompt settings' fields exactly.
- **AC8** — *the whole delta, as the chapter-10 alignment requires*: every one of the 127 scenarios of the 14 feature files is referenced by at least one test, and no test references a scenario absent from `requirements/` (the retired titles "the graph contains the four processing nodes" and "the graph starts both language detection and question rephrasing" no longer appear in any test docstring).
- **AC9** — *documentation consistency (5.2 "How the system is documented")*: the arc42 tree and the README describe the post-delta system — glossary entries for stage and SystemOne; the six-node graph in 5.2/7/8; the six-prompt family in I2 and 9.1; the extended `agent`-key range in 5.2, the glossary and the README MCP Server table; the 14-file/127-scenario tables in 03/10.2/13; the README Prompts table lists the two new keys with defaults equal to the chart's values (the unchanged repository-structure scenario "the documented prompt defaults match the chart defaults" machine-checks that table against the chart).
- **AC10** — *gate*: the repository's own `make test` target (flake8 lint, then `pytest .`, both via `uv` — the CI test job's entry point, 9.4/10.2) passes green.
