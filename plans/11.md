# Issue #11 — Align the test oracle with the extracted requirements (14 new feature files, 128 scenarios)

## Summary

Brownfield (full-derivation) run: the extraction created `requirements/` from the project's existing code, so **all 14 changed requirement files are new** and the baseline oracle knew none of their scenarios. This plan scopes the run to the test side only: the pytest oracle under `assistant/tests/` is adjusted to reference the 128 extracted scenarios — every scenario gets a referencing test (edited where a test already asserts the behaviour, added where nothing covers it yet) — and **no plan step implements or modifies product code**.

## Description

**Run shape.** The delta is the brownfield shape: every changed requirement file is new against the baseline (the extraction created the requirements directory). The requirements were extracted from the project's existing code, so the code already implements the behaviour the scenarios describe. Per the brownfield clause, this plan therefore (a) names the extracted scenarios it must cover and (b) scopes every step to *adjusting the tests to reference those scenarios* — no plan step implements code, and no step touches `requirements/*.feature`, `assistant/src/`, `infrastructure/`, `.github/`, `Tiltfile`, `Makefile`, `README.md`, or `LICENSE`.

**Documentation grounding (hard rule 2).** This repository carries **no arc42 document** (there is no `docs/` tree); the planning input is `README.md` plus the repository artifacts the README and the feature files describe. Where the README is silent (health probe thread internals, code-weaver workflow internals, MCP sampling internals), this plan grounds those steps in the corresponding existing source artifacts the extraction read (`assistant/src/assistant/endpoints/health_endpoints.py`, `.github/workflows/code-weaver.yml`, `assistant/src/assistant/impl/mcp_sampling.py`) and says so explicitly.

**Oracle shape.** The test suite is plain `pytest`/`pytest-asyncio` (per `assistant/pyproject.toml` dev extras — no behave/pytest-bdd or other Gherkin runner is a dependency), and **no existing test references any feature file**. The reference mechanism therefore lives in the pytest tests themselves:

> **Scenario-reference convention (fixed for all steps).** Each pytest test that implements an extracted scenario carries a reference in its docstring naming the scenario's verbatim `Scenario:` title and the feature file it comes from, e.g. `Implements "the health check repeats on a five minute interval" (requirements/health-api.feature)`. A test may reference several scenarios; each of the 128 extracted scenarios must be referenced by at least one test; no test may reference a scenario title that is absent from `requirements/`. The Gherkin text stays in the feature files (single source of truth) — tests never duplicate Given/When/Then lines. New or edited test modules must stay within the repository's existing flake8 test-file rules (`assistant/pyproject.toml` per-file-ignores), because the `make test` target runs lint + pytest and the CI test job runs both.
