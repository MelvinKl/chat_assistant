# Issue #15 — SystemOne model: goal-reachability determination on the chat graph, and per-stage MCP server filtering

**Summary**

The delta appends three new Gherkin scenarios to two existing feature files. Two extend the SystemOne model's role to the chat graph — at invocation it determines whether the user's goal can be reached at all with the available MCP servers, and an unreachable goal skips the stages up to the answer generation and answers that no MCP servers are currently available to help. One extends the question answering stages — when the stage LLM is created on a configured SystemOne model, the MCP servers available to the stage are filtered by that model. This plan implements the behaviour, adds the oracle tests for the new scenarios, restores the scenario-coverage guard, and updates the arc42 to the new state.

**Description**

The run's delta is a **standing in-place change** to two existing requirement files (both existed against the baseline; the additions sit at the end of unchanged surrounding content — this is *not* the brownfield full-derivation shape, so the steps implement code, not only test adjustments):

- `requirements/chat-graph.feature` gains two appended scenarios:
  - "the SystemOne model determines if the users goal can be reached"
  - "an unreachable goal skips the stages up to the answer generation"
- `requirements/stages.feature` gains one appended scenario:
  - "the SystemOne model filters the MCP servers available to a stage"

All three are **new** requirements (pure additions; no existing scenario in either file was changed, so no existing test needs editing for requirement drift). The work of this issue:

1. **Implement the new behaviour** in the components the arc42 documents:
   - the **chat graph** (`ChatGraph`, `impl/graph/chat_graph.py`, ch. 7.5) — a graph built with a configured SystemOne model must, on invocation with a user question, use the SystemOne model to determine whether the user's goal can be reached at all with the available MCP servers; when the goal is unreachable, the invocation skips the stages up to the answer generation and returns an answer informing the user that no MCP servers are currently available to help;
   - the **question answering stages** (`Stage`, `impl/stages/stage.py`, ch. 7.2/7.5) — a stage with a configured SystemOne model must have the MCP servers available to it filtered by the SystemOne model when the stage LLM is created.
2. **Add the pytest oracle tests** that implement the three new scenarios. The scenarios already exist in the feature files; **no new scenario or feature file is needed** — only the referencing tests.
3. **Re-align the machine-checked oracle** (the per-feature-file scenario coverage guard) and **update the arc42**, which currently documents the pre-delta state.

Arc42 context that shapes the plan: the SystemOne model is the optional fast decision model a question answering stage may run on (`SystemOneSettings`, env family `SETTINGS_SYSTEM_ONE_*`; a stage without one runs on the main LLM — glossary, ch. 7.3 I2). The chat graph is the six-node LangGraph `START → preprocessing → determine_language ∥ rephrase_question → decide → rephrase_answer → postprocessing → END` (ch. 7.5, glossary); its `ainvoke` already bypasses the compiled graph for empty input ("No question has been found.") — the documented pattern for an invocation-level short-circuit — and the single value the HTTP layer returns is the state's `processed_answer` (ch. 7.5, ch. 8 scenario 1). The oracle is plain pytest: each test cites the scenario it implements in its docstring, and `assistant/tests/test_scenario_coverage.py` verifies the alignment in both directions, parametrised per feature file (ch. 10); the gate is the repository's `make test` target (lint + pytest via uv).

## Acceptance Criteria

1. **A chat graph with a configured SystemOne model, invoked with a user question, runs the SystemOne model to determine whether the user's goal can be reached at all with the available MCP servers.**
   Fulfils the scenario *"the SystemOne model determines if the users goal can be reached"* (`requirements/chat-graph.feature`).
2. **When that determination concludes the goal cannot be reached with the available MCP servers, the graph's invocation skips the stages up to the answer generation, and the returned answer informs the user that no MCP servers are currently available to help.**
   Fulfils the scenario *"an unreachable goal skips the stages up to the answer generation"* (`requirements/chat-graph.feature`).
3. **A question answering stage with a configured SystemOne model and available MCP servers, when the stage LLM is created, has the MCP servers available to the stage filtered by the SystemOne model.**
   Fulfils the scenario *"the SystemOne model filters the MCP servers available to a stage"* (`requirements/stages.feature`).
4. **The oracle stays machine-aligned: every scenario of the two changed feature files — the three new ones and all unchanged existing ones — is cited by at least one test, no citation dangles, and the repository's `make test` gate (lint + pytest) is green.**
   Fulfils the standing alignment requirement of ch. 10 — the coverage guard `assistant/tests/test_scenario_coverage.py` (parametrised per feature file), which collectively guards every scenario of `requirements/chat-graph.feature` and `requirements/stages.feature`; the arc42 documents the new behaviour instead of the pre-delta state.
