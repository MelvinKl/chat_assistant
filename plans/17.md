# Issue #17 — The docker image CI job releases a new version on every push to `main`; the version number counts up with every release

**Summary**

The delta changes the release trigger of the docker image CI job. Where the
`docker-image.yml` workflow previously fired when a release was *published*
and tagged the image with that release's tag name, the changed scenario now
fires it when a change is *pushed to the `main` branch*, and the workflow
itself releases a new version of the assistant and tags the image with that
version number (the build, the push and the `latest` re-tag are unchanged).
One new scenario is appended to the same feature file: the version number
counts up with every release — a newly released version number must be higher
than the previously released one. This plan adds the counting-up release
mechanism to the workflow, re-wires the job to the push trigger, keeps the
pytest oracle aligned with the adjusted and the new scenario, and brings the
arc42 to the post-delta state.

**Description**

The run's delta is a **standing in-place change** to one existing requirement
file (`requirements/local-development.feature` exists against the baseline and
is modified — this is *not* the brownfield full-derivation shape), so the
standing instructions govern and the steps implement the delta, not only test
adjustments.

Per the baseline diff of `requirements/local-development.feature`:

| Scenario | Change |
|---|---|
| *the CI docker image job publishes release images* (existing, title unchanged) | **adjusted** — the When flips from `a release is published` to `a change is pushed to the main branch`; the first Then changes from `the assistant image is built and pushed tagged with the release name` to `a new version of the assistant is released` + `the assistant image is built and pushed tagged with the version number`; `And the image is re tagged as latest` is unchanged |
| *the version number counts up with every release* (appended) | **new** — `Given a released version of the assistant` / `When a new version of the assistant is released` / `Then the version number of the new release is higher than the version number of the previous release` |

The other nine scenarios of the file — and the other thirteen feature files —
are untouched, so their test citations stay valid; the oracle total moves
130 → **131 scenarios** (local-development 10 → 11).

**Contradiction with the arc42 the delta creates (hard rule 2, said and planned around).**
Chapters 8.4 (event table), 9.4 (provisioning row), 9.2 (image note
"tag = release tag"), 5 and 6 currently describe the `docker-image.yml` job
in pre-delta terms — triggered on `release: published`, image tagged with the
release tag — which the changed scenario contradicts (trigger is now the push
to `main`; tag is the version number the workflow itself releases). Chapter
10.2 declares the Gherkin files the single source of truth for behaviour, so
the delta wins and those arc42 statements are stale descriptions; the plan
resolves the contradiction in its final step by updating the documentation to
the post-delta state (the factory's standing practice, cf. the arc42 update
steps of `plans/12.md` and `plans/15.md`). Conversely, one element of the new
behaviour is *undocumented* in the arc42 anywhere: the mechanism by which a
released version number counts up. The plan grounds it in documented building
blocks — the `docker-image.yml` job and its pinned-action + run-script
convention (ch. 9.4, 10.1), and the assistant's version as the application
version the documented `/health`/`/readiness` payload carries (ch. 8.1
scenario 3, ch. 9.5) — and the documentation step records the chosen
mechanism.

**Oracle mechanics (chapter 10.2).** The coverage guard is parametrised per
feature file and checks both directions: from the baseline until step 1's test
lands, the new scenario is extracted-but-uncited (guard 1 red for
`local-development.feature`); the adjusted scenario keeps its existing
citation (the title did not change, so no dangling reference — guard 2 stays
green throughout). Steps 1 and 2 land the oracle edits, step 3 is the gate.

## Acceptance Criteria

1. **Adjusted — `requirements/local-development.feature`, *"the CI docker image job publishes release images"*.**
   When a change is pushed to the `main` branch, the `docker-image.yml`
   workflow releases a new version of the assistant, builds the assistant
   image from `assistant/Dockerfile`, pushes it to ghcr.io tagged with that
   version number, and re-tags the image as `latest`.
2. **New — `requirements/local-development.feature`, *"the version number counts up with every release"*.**
   Given a released version of the assistant, when a new version of the
   assistant is released, the version number of the new release is higher
   than the version number of the previous release.
3. **Standing alignment (ch. 10.2).** Every one of the eleven scenarios of
   `local-development.feature` — the adjusted CI docker image scenario, the
   new version counting scenario and the nine unchanged ones — is cited by at
   least one test; no test cites a scenario the oracle does not carry; and the
   repository's `make test` target (flake8, then pytest via uv) is green with
   the oracle at 131 scenarios. The arc42 documents the post-delta state:
   the push-to-`main` trigger, the release and counting-up version number the
   workflow creates, the version-number image tag, and the 131-scenario counts.

## Steps

- [x] **1. Make the version number count up with every release the workflow releases**
  - *Goal and its requirements.* The `docker-image.yml` workflow (the release
    images job of ch. 9.4) must derive the version number of every release it
    performs as strictly higher than the version number of the previously
    released version — the new scenario's Given (a released version of the
    assistant exists) means the derivation reads the repository's already
    released versions and computes the successor of the highest of them, so
    that every release counts the version number up. Fulfils the **new**
    requirement *"the version number counts up with every release"*
    (`requirements/local-development.feature`); the counting-up mechanism
    itself is undocumented in the arc42 anywhere (said in the description) —
    the plan grounds it in the documented job and its pinned-action +
    run-script convention, and step 4 records it in the documentation.
  - *The test that proves it.* Add a test to
    `assistant/tests/test_local_development.py` (the module that statically
    inspects the CI workflows — ch. 7.5 — and implements this feature file's
    scenarios), whose docstring cites `Implements "the version number counts
    up with every release" (requirements/local-development.feature)` and
    which asserts, against the parsed workflow, that the release step derives
    the new version number from the repository's released versions as
    strictly higher than the previous release's version number. The test pins
    only that derivation — not the trigger — so it passes both before and
    after step 2 re-wires the `on:` block. The scenario already sits in the
    feature file — no new scenario or feature file is needed, only the
    referencing test.
  - *arc42 context.* The released version number is the assistant's version:
    the application version the documented `/health`/`/readiness` payload
    carries (ch. 8.1 scenario 3, ch. 9.5). The arc42 does not yet document
    how release version numbers are assigned or counted up — ch. 9.4's job
    description only assumes them ("pushes the release tag"); step 4 moves
    that description to the counting-up mechanism.

- [x] **2. Trigger the docker image job on a push to `main`, and tag the released image with the version number**
  - *Goal and its requirements.* Re-wire the `docker-image.yml` job to the
    changed scenario: it must run when a change is pushed to the `main`
    branch (replacing the pre-delta `release: published` entry of its trigger
    block), and on that trigger it releases a new version of the assistant —
    the counting-up number of step 1 — then builds the assistant image from
    `assistant/Dockerfile` and pushes it to ghcr.io tagged with that version
    number (replacing the pre-delta tag sourced from the published release
    event's tag name), re-tagging the image as `latest` exactly as before.
    Fulfils the **adjusted** requirement *"the CI docker image job publishes
    release images"* — both its changed When (the trigger) and its changed
    first Then (the tag source) are the requirement drift this step absorbs;
    the Then lines about the build, the push and the `latest` re-tag are
    unchanged.
  - *The test that proves it.* Edit the existing
    `assistant/tests/test_local_development.py::test_ci_docker_image_job_publishes_release_images`
    — the scenario's title did not change, so its docstring citation stays
    and the prose describing the behaviour must be re-written to the new
    state. The expected outcomes that change in the test: the trigger
    assertion flips from `release: published` to a push on the `main` branch
    (the module's `workflow_triggers` helper over the parsed workflow), and
    the build step's tag assertion flips from the published release event's
    `tag_name` expression to the version number derived by step 1's release
    step. Unchanged and still asserted: the image is built from
    `assistant/Dockerfile`, pushed to ghcr.io, and re-tagged `latest`.
  - *arc42 context.* **The contradiction the delta creates:** ch. 8.4's
    event table row, ch. 9.4's provisioning row and ch. 9.2's image note all
    pin the job to `release: published` / "tag = release tag", and ch. 5 and
    ch. 6 repeat "published releases". The requirements — the single source
    of truth for behaviour (ch. 10.2) — now say push to `main` and
    version-number tag, so this step implements the requirement and step 4
    retires the pre-delta wording, not the other way round. The `test-and-lint.yml`
    PR gate (ch. 8.4) is untouched: it keeps validating pull requests to
    `main` while the docker image job now also runs on the push itself.

- [x] **3. Pass the machine oracle gate for the changed feature file**
  - *Goal and its requirements.* Keep the machine-checked alignment true for
    the whole oracle: with the tests of steps 1–2 landed, every one of the
    eleven scenarios of `local-development.feature` is cited by at least one
    test (the new scenario by step 1's test, the adjusted scenario by the
    edited test, the nine unchanged scenarios by their existing tests), no
    citation dangles, and the repository's `make test` target — flake8 lint
    then pytest via uv (ch. 10.2's gate) — is green with the oracle at 131
    scenarios.
  - *The test that proves it.* No new test is added — the guard
    `assistant/tests/test_scenario_coverage.py` **is** the test: it is red
    for `local-development.feature` from the baseline until step 1's test
    cites the new scenario, and this step verifies it is green per feature
    file with no dangling references, under the `make test` gate.
  - *arc42 context.* Ch. 10.2 documents the guard and the gate; its counts
    (local-development 10, total 130) are pre-delta — step 4 moves them to
    11 and 131.

- [x] **4. Update the arc42 to the post-delta state**
  - *Goal and its requirements.* The documentation tree must describe the
    new behaviour instead of the pre-delta state it currently carries: the
    `docker-image.yml` job triggers on a push to `main` (not
    `release: published`), on that trigger it releases a new version of the
    assistant whose version number counts up with every release, the
    published image is tagged with that version number (not the release tag)
    and re-tagged `latest`, and the oracle counts move from 130 to 131
    scenarios (local-development from 10 to 11) — including the stale 127
    counts the tree already carries in two places.
  - *The test that proves it.* No new test is added — the oracle of this
    behaviour is the feature file itself plus step 3's green guard (ch.
    10.2: the Gherkin files stay the single source of truth); the
    README-consistency scenarios of `repository-structure.feature` already
    pin the README's statements, and none of them names the workflow
    trigger, so the README needs no change.
  - *arc42 context — the contradictions this step resolves and their
    justification.* (a) ch. 8.4's event table row `release: published` →
    rewritten to the `main` push, with the job's new behaviour (releases a
    new version; version-number image tag; `latest` re-tag); (b) ch. 9.4's
    provisioning row for `docker-image.yml` — the same re-write, gaining the
    counting-up version derivation; (c) ch. 9.2's image note "tag = release
    tag" → "tag = version number"; (d) ch. 5's "the image is published by the
    release workflow" and ch. 6's "image build & push on published releases"
    → the push-to-`main` trigger; (e) the scenario counts: ch. 10.2's area
    table (local-development 10 → 11, total 130 → 131) and total line,
    ch. 7.1's oracle row, ch. 7.5's guard paragraph, `README.md`'s oracle
    line, and the two pre-existing stale "127 scenarios" statements in ch. 1
    and ch. 13 — all to 131. **Justification:** ch. 10.2 makes the Gherkin
    oracle the single source of truth, and ch. 5's documentation decision
    makes the arc42 the machine-actionable source the factory acts on —
    documentation that contradicts the oracle is a standing discrepancy the
    review stage flags, so the pre-delta trigger descriptions and the changed
    counts are updated in place, and the counting-up version mechanism gains
    its first documented home in the 9.2/9.4 job description.
