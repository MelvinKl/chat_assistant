# 11. Technical Risks

Risks and recorded inconsistencies of the system. Where a risk is also pinned
by the oracle, the feature file is named: the brownfield run (`plans/11.md`)
surfaced the findings as xfail-pinned tests, and the fix run that followed
reconciled risks 1, 7, 8, 9, 13, 14 and 15 — each row below records the
original finding and its reconciliation.

| # | Risk / inconsistency | Impact | Status |
|---|---|---|---|
| 1 | The README's Directory Structure lists a `components/` directory (`home-assistant`, `base-component-api`, …) that is **not present** in the repository tree; `.vscode/settings.json` still points analysis paths at `components/…` | Documentation–tree drift; onboarding confusion | Reconciled by the fix run: the README's Directory Structure no longer lists `components` (nor its `home-assistant` entry) and `.vscode/settings.json` no longer points analysis paths at `components/…`; the oracle (`tests/test_repository_structure.py::test_directory_structure_exists_in_repository`, `repository-structure.feature` scenario *the documented directory structure exists in the repository*) is green |
| 2 | The orphaned generated endpoint stubs (`endpoints/assist_endpoint.py`, `endpoints/get_description_endpoint.py`, and their `impl/endpoints/` counterparts) import the external `base_component_api` package, which is not in the tree and not a declared dependency (a remnant of the openapi-generator output, cf. `src/.openapi-generator/`) | An `ImportError` if anything were to import those modules; today nothing does (`main.py` mounts only the health router and the API routers) | Recorded; if the stubs are ever wired up, the generated package must be vendored or the imports removed |
| 3 | The health state is a module-level mutable global (`status`) plus a `Lock`, and the probe thread is started on the first `/health` call with no stop mechanism; each probe opens a client per server and runs `asyncio.run` per round | Process-wide state; an unbounded background thread; the status only ever moves toward `unhealthy` within a round | Design recorded (the `health-api` feature pins the current behaviour); a redesign is a later delta |
| 4 | `nest_asyncio.apply()` patches the process-wide asyncio event-loop policy at import of the container module | Affects every loop in the process, not just MCP loading | Required for `asyncio.run` inside uvicorn (chapter 4); recorded as a constraint |
| 5 | The models surface hardcodes a single model (`chat_assistant`, owned by *"No one. This model is a free spirit"*) regardless of the requested id | OpenAI clients that enumerate models see one entry; any model id resolves to it | By design (the `models-api` feature pins it) |
| 6 | The default `homeassistant` MCP server configuration carries placeholder connection values (`https://yoururl/mcp_server/sse`, `Bearer yourtoken`) | That subagent's tools are unreachable until an operator edits the values | Recorded in the README's MCP Server section |
| 7 | The chart's top-level values `features` (`qdrant: true`) and `egress` (`enabled: true`) are consumed by **no** template | Dead keys in the default values | Reconciled by the fix run: the top-level `features` and `egress` keys are removed from `infrastructure/helm/values.yaml`; the oracle (`tests/test_helm_deployment.py::test_default_values_contain_only_consumed_keys`, `helm-deployment.feature` scenario *the default values contain only keys consumed by the chart templates*) is green |
| 8 | `assistant-cm` renders a `SETTINGS_PROMPTS_MAX_TOOLS` key that no settings module reads (`PromptSettings` carries exactly the four rephrasing prompts) | A dead environment key in the assistant pod | Reconciled by the fix run: the `SETTINGS_PROMPTS_MAX_TOOLS` key is removed from `templates/assistant-cm.yaml` (the config map now carries exactly `SETTINGS_ADDITIONAL_INFORMATION`, the four prompt keys and — via the openai secret — the `SETTINGS_OPENAI_*` keys, all read by the settings models); the oracle (`tests/test_helm_deployment.py::test_rendered_assistant_environment_matches_application_settings`, scenario *the rendered assistant environment matches the settings the application reads*) is green |
| 9 | The sampling callback (`create_sampling_callback`) is created and unit-tested, but the container builds the MCP connection dicts **without** explicitly carrying it; the installed `langchain-mcp-adapters` does not forward a sampling callback in `create_session`, so sessions fall back to the `mcp` SDK's default sampling handler, which answers sampling requests with an error | MCP servers that request sampling get an error until the registration lands | Reconciled by the fix run: the container registers the callback on every MCP client connection — tool loading (`assistant_container._get_mcp_tools`) and the health probe (`health_endpoints.health_check`) both put `create_sampling_callback(llm)` under `session_kwargs` of each server's connection dict, the only route the installed langchain-mcp-adapters offers to the `mcp` SDK's `ClientSession` (its `create_session` forwards no sampling callback); the oracle (`tests/test_mcp_client_setup.py::test_sampling_callback_registered_on_every_connection`, `mcp-sampling.feature` scenario *the sampling callback is registered with every connected mcp server*) is green |
| 10 | A `SETTINGS_DYNAMIC_KNOWLEDGE_*` environment family appears in the `test_health_endpoints` fixture but no settings module reads it | Inert (every settings module sets `extra="ignore"`) | Template remnant; recorded |
| 11 | The ingress certificate secret and the `Certificate` resource carry a historical typo (`assitant-tls-certificate`), consistently in both places | Cosmetic; renaming would break an existing release's TLS secret | Recorded faithfully; a candidate for a later delta |
| 12 | The chart's assistant deployment runs `python -m uvicorn src.assistant.main:app` while the image's default `CMD` runs `uvicorn assistant.main:app` with `PYTHONPATH=/app/assistant/src` | Two entry spellings for the same app; both resolve from the image's workdir, but they diverge in readability | Recorded faithfully |
| 13 | The mcp server templates guard the **whole** egress network policy document with `{{- if $server.egress.enabled }}`, so with the default `egress.enabled: false` no policy is rendered at all for the mcp server pods; kubernetes allows all egress for a pod no network policy selects, so their egress is unrestricted — while the assistant deployment's include is unconditional and its disabled state renders a deny-all policy (`policyTypes: [Egress]`, empty egress) | The README’s “MCP servers have egress disabled by default for security” does not hold for the default deployment | Reconciled by the fix run: the guard is removed — `templates/mcp-deployment.yaml` now renders the egress network policy unconditionally, so an egress-disabled server (the default) gets the policy with the Egress policy type and no egress rule, which kubernetes reads as deny-all egress, and the README's “egress disabled by default” holds; the oracle (`tests/test_helm_deployment.py::test_mcp_server_egress_disabled_by_default`, scenario *mcp server deployments are egress disabled by default*) is green |
| 14 | The README's Prompts table documents the two user prompts without the final `Additional Information: {additional_info}` line the chart's default values carry (`assistant.settings.prompt` in `infrastructure/helm/values.yaml` renders the three-line version of `SETTINGS_PROMPTS_REPHRASE_QUESTION_USER_PROMPT` and `SETTINGS_PROMPTS_REPHRASE_ANSWER_USER_PROMPT`) | The documented defaults of those two prompt keys do not equal the chart defaults | Reconciled by the fix run: the README's Prompts table documents both user prompts with the final `Additional Information: {additional_info}` line, equal to the chart's defaults; the oracle (`tests/test_repository_structure.py::test_documented_prompt_defaults_match_chart_defaults`, `repository-structure.feature` scenario *the documented prompt defaults match the chart defaults*) is green |
| 15 | The README's Getting Started names `SETTINGS_HOMEASSISTANT_APIKEY` as a required `.env` secret, but no application settings model reads the variable and no chart template renders it into a deployment | The onboarding instructions name a secret the deployment never consumes — the live remnant of the `components/home-assistant` integration that is absent from the tree (cf. risks 1 and 6) | Reconciled by the fix run: the Getting Started section no longer names `SETTINGS_HOMEASSISTANT_APIKEY` — the only secret the README names is `SETTINGS_OPENAI_API_KEY`, consumed by both the application (`OpenAISetttings`) and the chart (`assistant-secret`); the oracle (`tests/test_repository_structure.py::test_named_environment_secrets_are_consumed_by_the_deployment`, scenario *every secret mentioned by the README is consumed by the deployment*) is green |
